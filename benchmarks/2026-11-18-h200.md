# One H200, four models, 2026-11-18

Four models benchmarked one after another on a single NVIDIA H200 (141 GB) on Northeastern's
Explorer cluster, with `hpc/benchmark-models.sbatch`. The load generator ran on the GPU node
itself, so no SSH tunnel or laptop is in these numbers. Raw rows:
[2026-11-18-h200.jsonl](2026-11-18-h200.jsonl).

## Setup

- vLLM v0.34.0 (CUDA 13) in Apptainer; GPU driver 570.86, so the job turned on CUDA's
  forward-compatibility libraries. One GPU, no tensor parallelism, `--max-model-len 8192`,
  default `--gpu-memory-utilization 0.9`.
- Each model: start vLLM, 15 s warm-up (not recorded), then 60 s at 1, 16 and 64 concurrent
  clients. Every request streams exactly 128 generated tokens (`ignore_eos`) from the same short
  prompt, so every model does the same work.
- Latency is measured per request on the client: request latency, time to first token (TTFT),
  and time per output token after the first (TPOT).

## What the numbers say

- **Single-stream speed is set by memory bandwidth.** Each generated token reads every active
  weight once: the 32B moves 61 GiB per token in 18.1 ms, about 3.6 TB/s, roughly three-quarters
  of the H200's ~4.8 TB/s peak. The 7B reaches about 3.2 TB/s.
- **Dense models batch almost for free here.** From 1 to 64 clients their time per token rose
  only 10–25%, so throughput grew 42–56× with latency nearly flat. Even at 64 clients the GPU was
  far from its limit.
- **gpt-oss-120b is as fast as the 7B for one user, but batches worse.** As a mixture-of-experts
  model with ~5 B active parameters in 4-bit, its single-stream speed matches the dense 7B. With
  more users, concurrent requests route to different experts, so its time per token rose from 4.5
  to 11.5 ms and throughput grew 24×, half the dense models' scaling.
- **Tails are tight.** At 64 clients, p99 request latency is within 21% of p50 for every model,
  and p99 time to first token stays under 175 ms.
- **The H200 alone, without the tunnel, more than doubles single-stream speed** compared with the
  earlier A100 runs through the control plane path ([2026-11-18-explorer.md](2026-11-18-explorer.md)):
  1.5B 199 → 474, 7B 93 → 209, 32B 24 → 55 tokens/s. Both the GPU and the shorter path contribute.
- **The GPU was doing work.** `nvidia-smi` sampled every 5 s showed it busy in about two-thirds
  of samples across both jobs; the rest is model loading between tests.

## Caveats

- One run per data point. The 1.5B ran in a separate job on H200 node d4054; the other three ran
  together on d4053. Same GPU model and driver.
- The first job's 7B row was discarded: its stop step left the 1.5B server running, so the
  1.5B answered in its place. The job script now uses a fresh port per model, stops vLLM itself,
  and checks which model is answering before measuring.
- Short prompts and 128-token outputs: this measures decoding, not long-prompt prefill.
- `nvidia-smi` utilization is the share of time any kernel was running, not how full the GPU was.
