# Explorer benchmark, 2026-11-18

Four models deployed by the control plane's Slurm backend to Northeastern's Explorer
cluster and load-tested through the full path: Mac → kind → SSH gateway → GPU node.
Raw rows: [2026-11-18-explorer.jsonl](2026-11-18-explorer.jsonl).

## Setup

- vLLM v0.34.0 (CUDA 13) in Apptainer; GPU driver 570.86 on every node, so the job script
  turned on CUDA's forward-compatibility libraries.
- One GPU per model, no tensor parallelism.
- Load test: `scripts/load_gen.py`, one model at a time, same prompt, exactly 128 generated
  tokens per request (`ignore_eos`), 1 client for 30 s and 16 clients for 60 s.
- Time to first token comes from vLLM's own histogram in Prometheus, over each test window.

| Qwen2.5-7B-Instruct | A100 80 GB (d1028) | 152.4 s / 205.6 s / 359.2 s ¹ | 14.3 GiB | 63.7 GiB (1.15 M tokens) |
| Qwen2.5-32B-Instruct | A100 80 GB (d1028) | 679.7 s / 625.8 s / 1307.5 s ² | 61.0 GiB | 12.6 GiB (47 k tokens) ³ |
| gpt-oss-120b | H200 141 GB (d4054) | 1075.3 s / 260.9 s / 1337.7 s | 61.4 GiB | 74.7 GiB (1.82 M tokens) |

¹ Startup includes the first download of the 15 GB of weights.
² Weights were pre-downloaded; reading 61 GiB from `/scratch` on d1028 took 504 s (~120 MB/s),
  versus 68 s (~900 MB/s) for gpt-oss-120b on d4054. Scratch read speed varied by node.
³ Started with `--gpu-memory-utilization 0.95 --max-model-len 8192`: about 6 full-length requests at once.

## What the numbers say

- **Dense models slow down with size roughly as memory bandwidth predicts.** Each generated
  token reads every weight once, so the 32B's 61 GiB at the A100 80 GB's ~2 TB/s caps a single
  stream near 30 tokens/s; it measured 24.
- **gpt-oss-120b on the H200 is the fastest per stream**, faster than the dense 7B on an A100:
  it is a mixture-of-experts model with about 5 B parameters active per token, stored in 4-bit,
  on a GPU with about 2.4× the A100's memory bandwidth.
- **16 clients did not saturate any of them.** Throughput grew about 15 to 17× from 1 to 16
  clients for every model; the 32B is the one close to a limit, since its cache holds only
  about 6 full 8 k-token requests.
- **Rollout time on Explorer is mostly queue wait and weight loading**, not vLLM itself.

## Caveats

Single runs; different GPU models and memory sizes; every request crossed the SSH tunnel
from a laptop, which adds latency. Good for comparing the models with each other, not as
absolute numbers. Repeat with more runs and higher concurrency before quoting them.
